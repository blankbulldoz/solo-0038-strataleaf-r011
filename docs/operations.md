# 恢复与观测

备份必须调用 archives.backup，不能只拷贝活动主文件。backup 与 restore 都不覆盖存在目标；恢复使用新路径，先校验来源 SHA-256，再打开新句柄。主库恢复生成新身份，副本恢复绑定来源。恢复清理原机保留点与消费者；消费方重新注册时须根据已恢复的 floor/head 判断是否需要重建。

## 增量备份链

备份链在完整基线之上追加分段，用于避免每次全量复制。流程是 `archives.backup` 发布基线、`chain.begin(baseline)` 登记链身份、每次 `chain.append(chain_id)` 取当前 head 生成一段。分段边界由调用方决定，一段可以覆盖任意多个提交，也可以只含目录变更（空提交段）。

一段是自描述 JSON 包 `{"body":…, "sha256":…}`。身份是 `(chain_id, seq)`；依赖是基线的 `(sha256, revision, catalog_epoch)` 与前一段的摘要和目录代数。包内不是当前活文档，而是该范围内每个提交的完整操作流：正文、显式删除墓碑、到期时间，以及该范围内发生的全部目录事件（集合模式与索引定义）。因此删除、模式演进和索引创建/移除都能重放，历史读也能在恢复库中成立。

`chain.verify` 校验单段：摘要、链身份、序号、基线依赖、前驱摘要与目录代数、提交号连续无缺口。`chain.plan` 校验整个有序前缀并给出可达目标。`chain.restore` 在触碰目标前完成全部校验，在临时文件中组装结果，只有逻辑自检与索引重算全部通过后才原子发布。缺段、乱序、身份不符、依赖不符或摘要错误都会抛 `ChainError`，不创建目标、不改动基线、也不覆盖已存在目标；`through=` 可以停在段内任意修订，重建到该读视图的模式与索引。

保留关系：`begin` 在基线修订处登记链持有水位，`append` 将其推进到最新段的 `through`。`retention.compact` 的 floor 不会越过任何链持有水位，所以已发布分段不会因为历史回收而变得无法重放。反过来，若回收已经越过上一段的 `through`（例如链登记在回收之后），`append` 会明确拒绝并要求重新取基线。

链分段由生产方保管；恢复方需要按 `seq` 顺序提供全部所需分段。`chain.discard(chain_id)` 退出链登记并释放其保留水位，用于更换基线或停止追加；已发布分段本身仍然自足，可继续用于恢复。校验和只证明内容完整，不提供来源身份认证。

diagnostics.inspect(deep=True) 检查 SQLite 完整性、外键、提交连续性、当前索引与文档投影；fingerprint 比较指定读视图的键、文档版本、内容及到期事实。前者不能证明所有业务数据正确，后者相同也不能代替模式与索引定义比对。checkpoint 返回 SQLite 的 busy、log、checkpointed 信息，并不承诺截断 WAL。

examples.observations 的 contention 会让独立连接暂持 IMMEDIATE 锁，记录第二句柄的 busy 超时及释放后的成功；retention_pressure 记录读保留点和消费者分别阻止水位推进的现象。它们用独立临时文件，不接触生产路径。观察包含真实修订和异常，适合复核运行边界。

关闭所有调用方句柄再移动数据目录；不支持共享网络盘或多主写入。在空间紧张时先核实 pin/消费者，推进已完成的确认后再回收；回收不自动缩小文件，物理容量由 SQLite 空闲页复用。到期清理只在显式调用时执行，不能把墙钟到期等同于读视图变动。
